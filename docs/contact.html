Where to go

Four doors in.

Everything happens in the open on GitHub — except security reports, which stay private until there's a fix.

Issues →

Found a bug, a wrong framework mapping, or an experiment that misgrades? Open an issue with the version or commit, repro steps, and what you expected. Clear, reproducible reports are gold.

Discussions →

Ideas for new experiment families, questions about the safety model, or a control you wish you could prove? Start a discussion before a big change — design in the open.

Contributing →

Pick up a good first issue, add a catalog experiment, or extend a signal source. The contributing guide covers the dev loop, tests, and the hard safety lines a change must respect.

Code of Conduct →

This is a welcoming, harassment-free community. By taking part you agree to uphold the Code of Conduct — read it before your first interaction.
Responsible disclosure

Found a way past the Safety Governor?

This is a security tool, so its own security matters most. Anything that could let a run bypass the Governor, forge an evidence receipt, or escalate a capability deserves a private, careful report.

Report it privately

Use the repository's Security → Report a vulnerability tab to open a GitHub Security Advisory, or email the maintainer listed on the repository profile. Include a description, affected version or commit, repro steps, and the impact.

Please don't

Don't open a public issue for an unfixed vulnerability, and never include real secrets, real PII, or working exploits in a report. Maintainers aim to acknowledge within 5 business days.

Read the full security policy →
One ground rule for everyone. Never point injection-mode experiments at a system you don't own or don't have written authorization to test. Read-only experiments are safe to run widely; injection experiments require the environment progression and approvals the Governor enforces. The project refuses to be a red-team tool — see the Charter.
